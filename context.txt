2. Core Project Idea

ForgeRT is intended to be a lightweight educational/research-oriented neural-network inference runtime.

The central research question is:

Given a neural-network computation graph and constrained heterogeneous hardware, can a lightweight runtime automatically choose where operations should execute based on compute cost, memory pressure, and CPU↔GPU transfer overhead?

The important idea is that:

GPU execution is not automatically faster.

For small operations, CPU execution may be preferable because copying data between CPU and GPU can cost more than the computation itself.

ForgeRT should eventually make these decisions automatically and transparently.

The runtime should be able to answer questions such as:

Should this operator execute on CPU or GPU?
Is moving this tensor to GPU worth the transfer cost?
Is GPU memory under pressure?
Would keeping an intermediate tensor on the CPU be cheaper?
Can adjacent operations be fused?
What execution placement minimizes total inference cost?

A major differentiating feature should be explainable/resource-aware scheduling, rather than simply being another inference framework.

3. Project Philosophy

The project should follow these principles:

Correctness first

Do not optimize code before correctness and independent testing are established.

Benchmark before making claims

Do not claim that GPU is faster merely because CUDA is being used.

Actual CPU/GPU measurements should eventually demonstrate when each backend is advantageous.

Transparent resource decisions

Scheduling decisions should be explainable.

For example:

MatMul → GPU
Reason:
  estimated compute cost: high
  transfer cost: low
  GPU memory available: sufficient

or:

ReLU → CPU
Reason:
  tensor is already resident on CPU
  operation is cheap
  GPU transfer overhead dominates
Explicit memory management

Memory ownership and transfers should be visible rather than hidden behind a framework.

Independently test backends

CPU and CUDA implementations should be testable independently and compared for numerical equivalence.

Avoid unnecessary dependencies

The runtime should remain lightweight and understandable.

Interview explainability

Every major architectural component should be something that can be explained clearly in a technical interview.

Do not artificially inflate the project

If an operator or optimization does not materially contribute to the runtime's goals, do not implement it merely to increase the feature count.

9. CMake 4.3 / CUDA Windows Issue

Another important build-system issue was discovered.

CMake 4.3's NVIDIA CUDA Windows configuration generated a CUDA compile command containing:

-Xcompiler=-Fd<TARGET_COMPILE_PDB>,-FS

The comma caused nvcc to interpret part of the command incorrectly, resulting in CUDA compilation errors.

The project was fixed by:

Stripping the problematic:
-Xcompiler=-Fd<TARGET_COMPILE_PDB>,-FS

suffix from:

CMAKE_CUDA_COMPILE_OBJECT

after project().

Scoping MSVC-specific flags such as:
/W4
/O2
/Zi
/Od

to C++ compilation only.

Adding:
-Xcompiler=/FS

to CUDA flags to avoid the MSVC PDB race/error:

C1041

These fixes are intentional and should not be casually removed.

41. Immediate Next Task — CUDA Softmax

The next intended milestone is:

Implement CUDA Softmax.

This should be the next focused task rather than jumping immediately into scheduling.

Why Softmax?

Because it exercises a different CUDA programming pattern from ReLU and MatMul.

ReLU is primarily:

elementwise

MatMul is:

tiled/shared-memory computation

Softmax introduces:

reduction

This gives ForgeRT multiple representative CUDA kernel patterns.

42. CUDA Softmax Requirements

The CUDA Softmax implementation should preserve the CPU operator's semantics.

Important requirements:

Last-dimension semantics

Softmax should operate along the last tensor dimension, consistent with the CPU implementation.

Numerical stability

Use:

x - max(x)

before exponentiation.

Avoid naïve:

exp(x)

without stabilization.

Actual CUDA reduction

Do not merely implement a serial CPU-like algorithm inside a CUDA kernel.

The CUDA implementation should demonstrate an appropriate reduction strategy.

Operator integration

SoftmaxOp should support:

Backend::CUDA

through the existing operator abstraction.

Error handling

CUDA errors should not be hidden.

CPU/CUDA equivalence

Results should be compared against the CPU implementation with an appropriate floating-point tolerance.
